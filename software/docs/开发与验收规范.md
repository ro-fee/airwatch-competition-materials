# 开发与验收规范

## 1. 文档与范围

- 《项目说明》维护项目统一口径，《参赛改造方案》维护目标方案，Word 任务书维护任务拆解。
- 已完成事项和实测结果写入《优化报告》或独立测试报告，计划与结果不得混写。
- 功能、指标或提交要求变化时只更新对应的权威文档，避免多份材料互相矛盾。

## 2. 数据与许可

- 每个外部数据集必须记录官方链接、论文、许可证、下载日期、版本和校验值。
- 原始数据只读保存；转换数据、切片和缓存写入独立目录。
- 数据划分以录制单元、设备或采集日期为最小分组单位，并提供自动泄漏审计。
- 仓库演示数据只允许用于流程测试，不允许进入正式指标表。
- 不将许可证禁止再分发的数据打入安装包或代码包。

## 3. 训练与实验

- 训练入口必须支持固定随机种子、设备选择、配置保存、断点恢复和最佳权重保存。
- 评估入口必须从固定测试清单读取数据，不得临时改变测试集或阈值。
- 所有结果由脚本生成 JSON/CSV，再由绘图或界面读取；禁止手工抄数和硬编码。
- 每个实验保存代码版本、环境、配置、数据版本、日志、权重和指标。
- 基线、主模型、消融和轻量模型必须使用同一数据划分与评估协议。
- 失败、无效和负向结果同样保留，材料中明确说明限制。

## 4. 软件实现

- `main.py` 是唯一维护中的启动入口；不要在 `main2.py` 的旧实现上继续开发。
- 所有新增功能同时考虑源码运行与 Windows 打包运行，不得依赖启动时的当前工作目录。
- 随软件分发的模型、冻结契约、标签映射、校准文件和静态资源按只读资源处理；运行结果、日志、缓存和用户配置必须写入用户可写目录，不得写入安装目录或 PyInstaller 临时资源目录。
- 文件路径通过统一运行时路径 Module 解析。新增相对路径、模型路径或输出路径时，必须增加源码模式与打包模拟模式测试。
- Windows 包只允许携带 `airwatch/runtime_resources.py` 从活动模型槽位和冻结契约派生的运行时资源闭包；禁止为了省事整棵复制 `models/`、`artifacts/` 或训练数据集。
- 已退休的磁盘图片渲染链不得重新引入 OpenCV；正式包验证必须拒绝顶层 `cv2`，并继续拒绝 pandas、torchvision、h5py、IPython 和 tensorboard 等训练/开发依赖泄漏。当前维护绘图使用 pyqtgraph 或内存 Matplotlib renderer。
- 打包、`release.json` 能力状态和发布验证必须消费同一份 `runtime-resources.json`。“预留”模型槽位不携带占位权重，不得在前端中显示为已可用。
- 每个前端可启用的模型功能都必须映射到一个明确的“可用”模型槽位；前端启动时应从槽位检查资源可用性，不得绕过清单使用新的硬编码权重路径。一个槽位只表达一个模型角色，历史轻量化对比不得复用未来竞赛端侧学生模型槽位。
- Windows 首次打包优先采用 `onedir` 形式完成依赖、Qt 插件、字体、模型资源和写权限验收；稳定后再评估 `onefile`，不得以“源码可运行”代替打包验收。
- 耗时的数据转换、模型加载、批量推理和报告导出必须迁移到 `QThread` 或线程池，不得阻塞 Qt 主线程。
- 后台任务需要进度、取消、异常回传和资源清理；后台线程不得直接更新 UI 控件。
- 历史信号生成必须通过不可变请求进入后台 Workflow；单次总量受内存预算限制，所有类别先写入同一隐藏暂存目录，完整成功后再提交唯一会话目录。取消或失败不得覆盖旧会话或留下可见的部分结果；批内信号统计偏离不得命名为 FID 或质量/准确率指标。
- 历史轻量化比较必须由 Data Module 校验清单版本、相对路径、大小、SHA-256、输入契约和冻结标签顺序，再由后台 Workflow 将同一窗口序列送入两个模型。软件演示清单的类别字段不得作为真实标签；在没有独立审计测试集时，OA、宏平均精度、F1、端侧时延必须保持未发布，窗口输出一致率必须明确标注为“非准确率”。成功后原子写入唯一 Evidence 目录，取消或失败不得留下部分结果。
- 模型服务输出统一的结构化结果，包括模型版本、标签映射、阈值、预测、置信度和耗时。
- 无人机文件预览和识别必须消费同一个只读“已准备输入”；质量检查覆盖完整记录，采样率必须来自用户或可信清单的明确声明，不能由模型契约反推输入事实。预览失败、质量拒绝、参数变化或准备未完成时，识别按钮保持禁用。
- 异常输入必须给出可理解的中文提示，不能静默失败或只打印堆栈。
- 界面中的实验指标必须来自结果文件，并能追溯到对应配置和测试清单。

## 5. 测试要求

每次改动至少执行与范围匹配的测试：

```powershell
python -m unittest tests/test_waterfall.py -q
python tests/smoke_test.py
python tests/smoke_test.py --models
python -m compileall -q .
```

完整回归使用：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run_tests.ps1
```

新增算法或软件模块时同步增加单元测试；修改主流程时增加集成测试。正式交付前还需完成 CPU 环境安装测试、连续运行测试、异常输入测试和三套固定演示场景测试。

发布包验收额外执行：

```powershell
powershell -ExecutionPolicy Bypass -File packaging/validate_portable_release.ps1
```

该检查必须逐文件验证运行时资源大小和 SHA-256，仅检查顶层目录存在不算通过。正式构建还必须从刚生成的可执行文件执行 CPU 模型自检，覆盖每个已发布模型角色的加载和有限值前向，并保存机器可读报告；该自检不得被描述为准确率评估。

## 6. 单项任务完成定义

一项任务只有同时满足以下条件才算完成：

- 代码、配置或文档已提交到约定位置。
- 自动化测试通过，并有必要的人工操作记录。
- 交付物满足 Word 任务书中的验收标准。
- 没有新增随机指标、硬编码结果、数据泄漏或无来源材料。
- 相关说明文档已同步更新。
- 失败路径、限制和降级方式已记录。

## 7. 参赛材料门槛

- 技术方案、PPT、视频、软件界面和报告中的数字必须与自动生成结果一致。
- 所有图表标明数据集、划分、指标和实验条件。
- 历史已有成果与本届新增贡献必须明确区分。
- 对外材料不得出现学校、指导教师等赛事禁止信息。
- 图片、字体、代码、论文和数据必须具备来源与授权记录。
- 演示视频使用真实软件录屏，不能以静态 PPT 冒充运行效果。
